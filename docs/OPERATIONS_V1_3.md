# 二次验证、加密备份、通知管理与合作交接 · v1.3.0

本版在 v1.2.0 的系统管理后台基础上实现四项功能。电脑和手机访问同一网站。默认不强制全站绑定第二因素、不启动自动备份、不自动给项目换群；上线前先执行 `0004_operations_security.sql`。历史账号、密码、项目、会签记录不会被重置。

代码完成与本地测试不等于云端已部署。真实 Cloudflare、认证器设备、模型、短信和企业微信尚须部署者验收；本次没有向真实服务商发送消息或支付费用。

## 1. 本人的账号安全与管理员二次验证

入口：左侧底部“账号安全”，手机先打开菜单。普通用户也可保护自己的账号；全站强制策略只有管理员能修改。

### 绑定与登录

1. 验证当前密码，选择绑定动态验证码。
2. 在本人可信认证器中**手动录入**网页显示的密钥，使用 TOTP、SHA-1、6位数字、30秒周期。本版不生成二维码、不向外部二维码服务发送密钥、不提供 Passkey。
3. 输入一组动态验证码，验证成功后才正式启用。待绑定密钥限时10分钟，且绑定当前登录会话。
4. 成功后一次性显示10枚恢复码，离线安全保管；关闭即清除显示。服务端只存恢复码散列，不提供查询原码。
5. 下次输入密码后，还须输入动态验证码或一枚未使用恢复码。第二步未完成前不能读取项目、账目、附件或后台数据。

验证码允许相邻时间窗口以容忍少量时钟偏差，但同一验证码不能再次使用。每个账号五分钟最多8次验证码尝试。新登录的待验证会话有效5分钟；验证完成会轮换会话与CSRF标记。代码使用 RFC 6238 算法并以标准测试向量验证，但未测试用户实际认证器设备。

已绑定的管理员进行配置变更、敏感管理操作或下载全站备份时，还需最近5分钟内的第二因素验证，并保留原有密码再验证。刷新页面不会自动代填验证码。

### 恢复、换设备和全站策略

恢复码只能消费一次，使用后记录管理日志。已登录且重新验证本人后，可以重新生成恢复码，旧码全部失效；新码仍只显示一次。更换手机之前应安排好恢复方式，不要先删除旧认证器。

“系统管理 → 二次验证”展示各管理员绑定状态。先让全部现有有效管理员完成绑定、保存恢复码，再开启强制策略。策略开启后，后续新管理员未绑定时不能进入后台，但仍可进入自己的账号安全完成绑定。管理员不能通过重置他人密码来消除其第二因素。

策略默认不强制，以避免升级把旧管理员全部锁在门外；一旦某账号自己启用，登录该账号就始终需要第二因素。强制策略下，管理员不能直接关闭自己的绑定，须先经验证调整策略。

遗失设备与全部恢复码时，没有公开的“万能验证码”或默认密码后门。可信部署者应在隔离环境核实身份、备份与恢复方案；不能随意改数据库绕过真实合伙人的审批。`CONFIG_ENCRYPTION_KEY` 用于加密动态验证密钥及服务商配置，丢失后应从安全保管处恢复，不能重新生成冒充旧密钥。

## 2. 自动加密备份与独立恢复演练

入口：“系统管理 → 备份与恢复”。**开启计划不表示已有成功备份**：页面显示每次排队、执行、完成或失败的真实记录，以及最近成功时间。计划启用但尚未成功，或距离最近成功捕获已超过36小时，页面显示告警；Cron运行时也会记录站内告警。

### 资源与密钥

| 绑定/变量 | 用途 | 必要隔离 |
|---|---|---|
| `DB` / `FILES` | 现有生产数据库、业务私有附件 | 保留原绑定 |
| `BACKUPS` | 加密备份专用私有 R2 桶 | 不得等于 FILES |
| `RESTORE_DB` | 数据恢复演练专用 D1 | 不得等于生产 DB，只能是专用空库或本模块既有演练库 |
| `RESTORE_FILES` | 演练解密文件专用私有 R2 | 与 FILES、BACKUPS 均不同 |
| `FILES_BUCKET_NAME`、`BACKUP_BUCKET_NAME`、`RESTORE_BUCKET_NAME` | 真实桶名声明 | 必须匹配 Wrangler 中的 bucket_name，不能只改别名假装隔离 |
| `BACKUP_ENCRYPTION_KEY` | 独立32字节随机密钥的base64，部署Secret | 不得与CONFIG_ENCRYPTION_KEY相同，不存数据库/页面/Git |
| `BACKUP_OLD_KEYS_JSON` | 可选旧密钥环，部署Secret | JSON对象：旧指纹→旧密钥base64；供读取轮换前的备份 |

`npm run check` / `npm run check:bindings` 校验当前配置文件的资源声明；运行时再次检查绑定。使用自定义 Wrangler 环境或其他发布工具时，部署者必须核对实际生效配置与真实资源ID，不能仅凭变量名称确认隔离。演练开始前还检查目标库现有表名；检测到生产表、其他业务表或不正确隔离标记会停止，不写入。

### 备份内容与自动化

数据库中的用户、项目、财务、审计、邀请、配置、AI历史、通知记录和第二因素数据均包含在备份中；包括归档及回收站项目。业务数据来自一次事务批次的快照读取。对应的**全部已登记附件**逐份读取并与登记尺寸/哈希核对，缺文件、文件被改或超限会失败，不显示“完整备份成功”。

每个数据库/附件部件使用 AES-256-GCM 独立加密认证；清单同样加密，下载的 `.hhyx.tar` 只包含密文、非秘密格式元信息和密钥指纹。后台下载不提供解密根密钥。密码是原有散列，服务商Key和TOTP密钥在数据库内还有配置根密钥加密层；这些数据仍高度敏感。

部署 Secrets、域名、外部服务商账户、R2/D1权限等**不在数据库备份中**，须另行安全保管。活动登录会话、临时限流和正在执行的备份任务不恢复；恢复后不能复用旧会话直接登录。

可以手动创建，或设置每日UTC某一小时之后由现有Cron调度。任务按UTC日期去重，一个站点同时只执行一个备份或演练；执行采用分段、租约与可重复领取机制。每轮调度推进有限步骤，大量附件可能需要多轮Cron，不承诺整点完成。失败不伪装成成功，也不自动删掉失败证据；人工新建任务可重试。

自动演练是独立开关：备份完成后，排队执行数据恢复验证。调度依赖已正确部署的Cron、资源与配额；没有Cron或服务不可用时不会凭空完成。通知、AI、备份的调度分开处理，某一项失败不会跳过其他任务。

### 真正的恢复演练，而非只检查文件存在

演练将已认证解密的表结构、数据写入**独立 RESTORE_DB** 的本次任务命名空间，并将附件写入 **RESTORE_FILES** 的本次目录。随后从恢复目标重新读取，逐表核对数据哈希与条数，检查外键、项目审计链和AI报告哈希，逐份核对附件哈希。

每次演练使用新命名空间，不删除或覆盖以前演练，更不向原生产库/业务桶恢复。报告明确标记 `productionWritten:false`。目标演练库/桶包含解密后的敏感资料，仍须私有、限制权限与留存。

**演练通过仅表示该份数据按这些检查成功恢复，不是完整业务站点灾备切换、域名恢复、外部通知或登录设备验收。** 本版没有“用旧备份覆盖生产”按钮，也不会自动回滚已发生的真实交易。

### 原站点不可用时：离线恢复校验

随源码提供 `scripts/restore-drill.mjs`，不依赖原站点、Cloudflare凭据或外部网络。需要Node.js 22.16.0及对应备份密钥。通过可信Secret注入方式给当前进程设置 `BACKUP_ENCRYPTION_KEY` / 可选 `BACKUP_OLD_KEYS_JSON`，不要把值写进命令、日志或聊天。

```bash
# archive替换为已下载归档，output必须是尚不存在的新目录（源码目录之外）
node scripts/restore-drill.mjs \
  --archive /secure-input/hhyx-backup-example.hhyx.tar \
  --output /secure-restore/new-isolated-drill
```

工具拒绝覆写已有输出目录、危险归档路径、错误密钥、清单/数据库/附件不一致。它创建仅本人可访问的新目录，在其中恢复SQLite和文件，生成 `attachment-map.json` 与 `restore-report.json`；失败保留独立失败标记。不会启动网站、发送通知或运行模型。这个SQLite是数据演练产物，**不能未经迁移/配置核对就当成应用的现成生产数据库**。

### 容量、留存和费用边界

本版为小团队设计：单份数据库快照最多16MiB，每张业务表最多10000行，最多1000份附件，每份最多10MiB。超限明确停止，不截断资料；更大数据库须先改用运维D1导出与R2备份流程或扩容开发。实际Workers CPU、内存、D1查询/批次与R2吞吐须在目标计划下验证，本地测试不证明云端配额足够。

没有自动清理或保留期删除功能；历史备份、演练、失败任务的部分密文和演练文件会持续占用存储。管理员须在核实独立备份、留存义务、敏感数据权限及费用后，安排受控的运维归档清理。本版没有自动跨账户/跨区域副本，建议另行安全保存下载的密文与分别保管的密钥。

更换备份根密钥后，旧备份只有在提供相应旧密钥环时才能读取；不能通过新Key解密旧数据。配置根密钥与备份根密钥的保管都必须纳入恢复演练。

## 3. 全站通知服务商与投递告警

入口：“系统管理 → 通知服务商”和“投递与告警”。只有系统管理员能读写这些配置接口。新增Web配置不改变已有站内待办和成员权限。

支持全站外发总开关、企业微信内部群Webhook、阿里云AccessKey ID/Secret、短信签名/模板、每日发送尝试额度和简短管理员告警。Key及Webhook加密保存、不回显；留空保留，清除需同时关闭对应渠道。第一次后台保存后数据库配置优先；关闭或清除后不会回退旧部署变量中的Key。

**保存配置不发送消息。** 测试是独立操作，需要再次验证、明确接收范围和可能费用；每小时全站最多5次测试。企业微信只发一条不含项目资料的测试句；短信只能发给发起管理员本人已登记且已同意短信的手机号。签名与模板须由实际服务商审核，模板变量沿用 `project` / `title`。不实现任意手机号群发。

### 项目范围与个人同意

全站Webhook必须填写“接收群名称、适用项目及获授权成员范围”。项目负责人在本项目通知页可选择关闭、项目自有群，或**看过该范围后明确确认继承全站群**。不是所有项目自动向同一群发送；群里没有权限的人不能因软件一个开关就被视为获授权。系统无法核实真实群成员，由配置人与项目负责人负责核实。

配置版本变更后，继承全站群的项目显示“需重新确认”，未确认不继续向该群投递。项目自有群仍可独立配置。后台总开关关闭时，项目自有群、全站群和短信均停止后续外发；已经发出的请求无法撤回。

短信仍要求本人主动同意。应用按UTC日期限制1–1000次发送尝试/天，每个用户每小时最多5次；未知/超时也占用额度，不当作免费失败。这个额度不是服务商账单或硬消费上限，实际账号还应设置服务商预算和告警。

### 失败与重发

投递页保留原始失败/结果不确定记录。管理员核对服务商回执并确认重复/计费风险后，可创建新的重发记录，原记录不被擦掉或重置。普通项目负责人重发也保留原记录。

渠道接受请求不等于送达、已读或批准。终止失败、备份失败和调度异常形成站内管理员告警；可显式开启向已授权管理员群发送不含项目细节的简短告警，不自动把项目财务发到全站群。关闭告警外发不删除站内记录。管理日志不保存密码或Key，原始服务商响应不直接回显。

## 4. 项目所有权移交与合伙人退出清算

入口：项目导航“移交与退出”。这是项目治理流程，不是管理员接管按钮；需要相应项目身份。归档项目只读。

### 移交负责人

原负责人发起，选择本项目另一名已加入的有效合伙人，说明资料、权限、渠道与职责交接安排。冻结原全体合伙人名单，会签时接收人必须额外明确勾选“接受负责人职责”。全部同意后才改变 `ownerId`；原创建人与历次移交记录保留。原负责人仍是合伙人，分配比例不会因负责人变更自动改变。

### 退出流程

```text
拟定退出方案与工作交接
→ 原全体合伙人会签，退出本人明确接受
→ 进入清算中，退出者仍保留成员与表态权
→ 登记真实净收付款，由其他人独立复核
→ 原全体合伙人再次确认完成
→ 正式退出，应用约定的新比例，保留全部历史
```

当前负责人先移交，再申请退出。退出后至少保留两位合伙人；两人项目不能借退出向导变成单人采购，须先结束业务、处理款项并归档。一次只处理一份退出清算。

向导要求逐项填写约定返还出资、约定利润、偿还垫款、成员补缴/抵扣、金额依据、库存/未结责任处理、合同和争议安排、截止日期。剩余合伙人的比例须合计100%，不会由AI或管理员自动猜分配规则。

所有与退出者有关的未完成任务、采购执行和验收都必须指定交接人员，仍保留不同的执行人和验收人。相关款项、成员或工作资料在会签中变化时，旧方案不能继续无视变化自动生效；需要重新核对。

约定净额 = 返还出资 + 本次利润 + 偿还垫款 − 补缴/抵扣。正数由项目实际支付，负数由成员实际缴回，零元仍需要完成两轮共同确认。不能自动转账，不能把成员出资返还当成经营成本。可分配利润和可用资金只根据内部已记录、已核实资料检查，不是审计报告或法律结论。

清算生效后预占正净支出资金，暂停新增采购和冲突的成员/分配调整；现有事项仍可执行、记账和核实。实际收付可分次，累计不能超过批准净额，记录凭证，并由不同成员复核。实际款未足额核实、交接不完整或有未核实账目时，不能完成退出。

最终确认中退出者依然有一票；全部通过后才设为非活跃成员并调整比例，旧签名、账目和责任说明保留。尚未发生真实退出收付款时可以另行全员同意取消方案；已经发生真实款项时不允许简单取消抹掉事实，需协商后通过受控处理。

有分配比例的合伙人不能通过旧“移除成员”入口跳过清算；没有比例的成员清理仍按原会签和未完成事项检查执行。暂停账号不等于退出，也不会偷偷减少必签人数。

本功能记录共同约定与真实执行，不决定某人依法必须赔多少，也不自动解除合同、债务、担保、税费或第三方权利。存货估值、争议、法律和税务事项需要当事人核实并按适用要求处理。

## 5. 升级、故障和证据

先按 `HERMES_DEPLOY.md` 备份现有D1、R2和配置，再增量迁移0004并部署。不要重建账号或重复执行原始ALTER脚本，不要直接回滚到忽略MFA/清算/归档限制的旧代码。管理入口有版本不等于线上已升级。

复现测试、已验证和未验证范围见 `ACCEPTANCE_V1_3.md`。需要停止上线的情况：迁移失败、绑定与生产重复、恢复目标存在其他业务表、根密钥缺失、越权测试失败、无法保持备份/演练私有、没有费用或接收范围授权。
